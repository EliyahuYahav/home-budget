1

בקצרה

מונוליט Next.js שרץ כ־serverless ב־Vercel, מעל Postgres מנוהל של Supabase. גבול האבטחה הוא המסד עצמו (Row Level Security), ולא שכבת ה־API. לצד זה יש worker שרץ ברשת הביתית, מושך עבודות מטבלה במסד ונכנס לבנקים עם דפדפן אמיתי.

  • שכבת התצוגה: React Server Components, עם קומפוננטות לקוח רק היכן שיש אינטראקציה. האתר מותקן בטלפון כ־PWA.
  • שכבת האפליקציה: Server Actions (src/app/actions.ts) כנקודות הכניסה לכתיבה, ולוגיקה עסקית כפונקציות טהורות ב־src/lib (budget.ts, trends.ts), בלי I/O.
  • שכבת הנתונים: Postgres עם 11 טבלאות, RLS על כל טבלה, ושלוש פונקציות security definer לפעולות שחוצות משקי בית (פתיחה והצטרפות).
  • שני לקוחות של המסד: האתר, וה־sync agent. שניהם מתחברים כמשתמש רגיל עם JWT, ולכן אותן מדיניות RLS חלות על שניהם.
  • מסלול אחד עוקף RLS: ה־cron של הדוח החודשי, עם service_role, שמבודד למודול אחד ומוגן בסוד.
2

הכוחות שמעצבים את המערכת

כל החלטה בהמשך נגזרת מהאילוצים ומסדר העדיפויות כאן. כשהם ישתנו, חלק מההחלטות יצטרכו להשתנות איתם.

אילוצים

אילוץמה הוא אומר בפועל
צוותמפתח אחד עם עוזר AI. אין מי שיתחזק שרתים, יעדכן מערכות הפעלה או יקום בלילה לתקלה.
תקציבקרוב לאפס. מסלולים חינמיים של Vercel ו־Supabase. העלות המשתנה היחידה היא Claude, וכל משק בית משלם עליה בעצמו.
היקף2 משתמשים למשק בית, כמה משקי בית, כמה אלפי תנועות בשנה לכל אחד. לא צריך לתכנן לסקייל.
ריבוי מכשיריםשני בני זוג, טלפונים ומחשב, אותם נתונים בזמן אמת. לכן הנתונים חייבים לשבת בשרת ולא במכשיר.
בנקיםלבנקים בישראל אין API פתוח לאדם פרטי. הגישה היחידה היא scraping של אתר הבנק עם דפדפן, כולל קוד ב־SMS לפעמים.
רגישותנתונים פיננסיים, ופרטי כניסה לבנק. דליפה כאן היא נזק אמיתי.

מאפייני איכות, לפי סדר עדיפות

  1. אבטחה ופרטיות. בידוד מוחלט בין משקי בית, ופרטי בנק שהשרת לא יכול לקרוא.
  2. נכונות של החשבון. סכומי כסף, כפילויות מהבנק, חודשים שחוצים תאריכים. טעות כאן הופכת את האפליקציה לחסרת ערך.
  3. מעט תפעול ומעט עלות. כל רכיב שצריך לתחזק הוא רכיב שיתקלקל בלי שמישהו ישים לב.
  4. מהירות בטלפון. רישום הוצאה צריך לקחת שניות, אחרת לא רושמים.
  5. ניידות. אפשרות לעזוב ספק בלי לכתוב הכול מחדש. חשוב, אבל אחרון ברשימה.

קונטיינרים וגבולות אמון

תצוגת C4 ברמה 2: התהליכים שרצים, איפה הם רצים, ובאיזה פרוטוקול הם מדברים. המסגרות המקווקוות הן גבולות אמון.

דפדפן ← Vercelcookie עם session של Supabase. פרטי בנק עוברים רק אחרי שהוצפנו בדפדפן.מפתחות שרת. הדפדפן מקבל רק את המפתח הציבורי (publishable) של Supabase.

4

למה Supabase ולא שלוש שכבות קלאסיות

זו ההחלטה שהכי משפיעה על כל השאר, ולכן היא מקבלת פרק משלה. השאלה היא למה לא בנינו front, back ו־database נפרדים: React SPA, שרת API (Express, NestJS או ‎.NET) שמדבר עם Postgres, ומערכת התחברות שכתבנו בעצמנו.

חשוב להבין: לא ויתרנו על השכבות. גם כאן יש תצוגה, לוגיקה ונתונים. ויתרנו על תהליך API נפרד ועל אכיפת הרשאות בקוד האפליקציה. שרת Next.js הוא ה־backend, ו־Postgres הוא המסד. ההבדל הוא איפה יושב גבול האבטחה ומי מחזיק את שכבת הגישה לנתונים.

הנימוקים שהכריעו

  1. יש שני לקוחות למסד, לא אחד. הסוכן בבית צריך לקרוא בקשות סנכרון, לקרוא פרטים מוצפנים ולכתוב תנועות. בארכיטקטורה קלאסית זה אומר עוד סט endpoints, עוד אימות ועוד בדיקות. עם Supabase הסוכן מתחבר כמשתמש רגיל ומקבל את PostgREST עם אותן מדיניות RLS שהאתר מקבל. אין קוד הרשאות שני שיכול לסטות מהראשון.
  2. ההרשאות יושבות היכן שהנתונים נמצאים. בגישה הקלאסית כל endpoint חייב לזכור להוסיף where household_id = ?. מספיק endpoint אחד ששכח, ומשק בית אחד רואה נתונים של אחר. עם RLS, גם שאילתה ששכחה את התנאי מחזירה רק שורות שמותרות. הקוד עדיין מסנן לפי משק בית, אבל זו שכבה שנייה ולא היחידה.
  3. התחברות היא קוד שלא כדאי לכתוב לבד. hashing, rotation של tokens, איפוס סיסמה, אימות מייל, הגנה מ־brute force. Supabase Auth מוציא JWT חתום (ES256) שגם המסד מבין (auth.uid()) וגם השרת מאמת מקומית (getClaims), בלי round-trip.
  4. זה עדיין Postgres. בניגוד ל־Firebase, הנתונים רלציוניים: סכומים לפי קטגוריה וחודש, unique על מזהה מהבנק, foreign keys עם cascade, ו־numeric(12,2) לכסף. אפשר לעשות pg_dump ולעבור לכל Postgres אחר.
  5. אין שרת API שצריך להחזיק. מפתח אחד לא יכול לתחזק שני שירותים, CI לשניהם, ניטור לשניהם, ותיאום גרסאות ביניהם.

המחיר

  • הלוגיקה מפוצלת בין SQL ל־TypeScript. מדיניות RLS ופונקציות security definer כתובות ב־SQL, השאר ב־TS. מי שקורא את הקוד צריך להכיר את שניהם.
  • קשה יותר לדבג RLS. מדיניות שחוסמת לא זורקת שגיאה בקריאה, היא מחזירה רשימה ריקה. בגלל זה יש 70 בדיקות שמריצות את הסכמה על PGlite (Postgres בזיכרון) ומנסות לפרוץ אותה.
  • נעילה ל־Supabase Auth. המשתמשים יושבים בסכמה auth ש־Supabase מנהל, והמדיניות קוראות ל־auth.uid(). מעבר לספק אחר דורש להעביר משתמשים ולהחליף את הפונקציה.
  • אין API ציבורי מתועד. Server Actions הם RPC פנימי של Next.js. אם תהיה אפליקציה native, היא תדבר עם PostgREST ישירות או שנצטרך להוסיף API.
  • תלות במסלול החינמי. בתוכנית החינמית Supabase משהה פרויקט שלא היה בו שימוש תקופה מסוימת. הסנכרון היומי שומר אותו פעיל, אבל זו תלות שכדאי לזכור.

מתי זו הייתה בחירה לא נכונה

אם היו כאן לוגיקה עסקית כבדה בצד השרת, הרבה אינטגרציות שצריכות orchestration, צוות עם backend developers, או לקוחות חיצוניים שצריכים API יציב, ארכיטקטורה קלאסית עם שכבת שירותים מפורשת הייתה נכונה יותר. כאן הלוגיקה היא בעיקר חישוב על נתונים קטנים, והיא רצה כפונקציות טהורות בכל מקרה.

5

רשומות החלטה (ADR)

כל ההחלטות המשמעותיות. כל אחת עם ההקשר שלה, החלופות, המחיר, ומה ישנה אותה.

ADR-01

מונוליט Next.js עם Server Components ו־Server Actions

הקשר
צריך UI מהיר בטלפון, שרת שמחזיק סודות (מפתחות Claude), וכתיבות עם אימות. מפתח אחד.
החלטה
אפליקציית Next.js אחת. קריאות נעשות ב־RSC ישירות מול המסד (src/lib/data.ts). כתיבות עוברות דרך Server Actions. אין שכבת REST.
חלופות
  • SPA + REST API: שני deployables, DTOs כפולים, ו־waterfall של fetch בצד הלקוח. נדחה בגלל עלות התחזוקה.
  • tRPC או GraphQL: נותן type-safety מקצה לקצה, אבל Server Actions נותנים את אותו דבר בלי שכבה נוספת.
  • Remix או SvelteKit: מתאימים באותה מידה. Next.js נבחר בגלל האינטגרציה עם Vercel והאקוסיסטם.
השלכות
  • טיפוסים משותפים מהמסד עד הקומפוננטה, בלי סריאליזציה ידנית.
  • דף נטען עם הנתונים בתוכו (streaming עם Suspense), בלי spinner ראשוני.
  • Next.js 16 שונה מהתיעוד הישן: proxy.ts במקום middleware, ו־cacheComponents שמחייב שכל גישה ל־cookies תהיה מאחורי Suspense. לכן יש loading.tsx בכל תיקיית מסך.
  • Server Actions הם endpoints ציבוריים. כל action חייב לאמת בעצמו, וזה נעשה דרך requireContext.
לחזור אם
תידרש אפליקציה native או לקוח צד שלישי שצריך API יציב ומתועד.
ADR-02

Supabase כמסד, Auth ו־API לסוכן

הקשר
מפורט בפרק 4.
החלטה
Supabase (Postgres מנוהל, GoTrue, PostgREST). הלקוח בשרת נוצר עם המפתח הציבורי וה־session מה־cookie (@supabase/ssr), כך שכל שאילתה רצה כמשתמש ולא כמנהל.
לחזור אם
המסלול החינמי לא יספיק, או שיהיה צורך ב־Auth שלא נתמך (SSO ארגוני, למשל).
ADR-03

הרשאות ב־RLS כגבול האבטחה הראשי

הקשר
נתונים פיננסיים של כמה משקי בית באותו מסד. דליפה בין משקי בית היא הכשל החמור ביותר האפשרי.
החלטה
RLS על כל 11 הטבלאות. המדיניות נשענות על is_household_member(household_id), פונקציית security definer שבודקת את auth.uid() מול household_members. ל־anon אין שום הרשאה (revoke). בטבלאות רגישות יש גם הרשאות ברמת העמודה: חבר לא יכול לשנות את קוד ההזמנה או את max_members.
חלופות
  • אכיפה בקוד בלבד: נקודת כשל אחת. כל שאילתה חדשה היא הזדמנות לשכוח.
  • Repository layer שמוסיף את התנאי אוטומטית: עדיף על כלום, אבל לא מגן על הסוכן, שלא עובר דרכו.
השלכות
  • Defense in depth: באג באתר או בסוכן לא חושף נתונים של משק בית אחר.
  • אפשר לבדוק את המדיניות בבידוד (npm run test:db, על PGlite).
  • המדיניות רצה על כל שורה. בהיקף הזה זה זניח, ויש אינדקסים על household_id.
  • פונקציות security definer עוקפות RLS. כל אחת מהן צריכה לבדוק הכול בעצמה ולקבוע search_path.
ADR-04

Multi-tenancy: סכמה משותפת עם household_id

הקשר
האפליקציה נפתחה למשפחות נוספות. כל משפחה היא tenant.
החלטה
Pool model: כל הטבלאות משותפות, ולכל שורה יש household_id. unique(user_id) ב־household_members מבטיח שמשתמש שייך למשק בית אחד בלבד. ההצטרפות עוברת דרך join_household, שאוכפת max_members = 2.
חלופות
  • סכמה לכל tenant: בידוד חזק יותר, אבל migrations כפול מספר המשפחות, ו־PostgREST לא בנוי לזה.
  • מסד לכל tenant: מתאים לרגולציה כבדה. כאן זה פרויקט Supabase לכל משפחה, וזה לא מעשי.
  • משתמש שיכול להשתייך לכמה משקי בית: נדחה. כל שאילתה הייתה צריכה לדעת מה משק הבית "הפעיל".
השלכות
  • כל שאילתה פשוטה: "השורות של משק הבית שלי".
  • הבידוד תלוי לגמרי בנכונות של RLS (ADR-03), ולכן יש עליו בדיקות.
  • קוד ההזמנה הוא 8 תווים הקסדצימליים (32 ביט). זה בסדר רק כי משק בית נסגר אחרי שני חברים ו־Auth מגביל ניסיונות.
ADR-05

לוגיקה עסקית כפונקציות טהורות, ומצב נגזר בזמן קריאה

הקשר
"מותר להוציא היום", קרנות, יעדים וארנק המזומן תלויים כולם באותן תנועות. הכללים השתנו הרבה במהלך הפיתוח.
החלטה
המסד שומר רק עובדות: תנועות, קטגוריות, הגדרות. כל מה שנגזר (יתרות, יתרת קרן, נצבר ליעד, חלוקת המזומן) מחושב בכל בקשה בפונקציות טהורות ב־src/lib/budget.ts: summarizeMonth, fundStatus, goalStatus, settleCash. אין I/O בתוכן. האתר, הבוט והדוח קוראים לאותן פונקציות.
חלופות
  • יתרות שמורות שמתעדכנות בטריגרים: מהיר בקריאה, אבל כל שינוי בכלל דורש migration של נתונים, ובאג משאיר יתרות שגויות לתמיד.
  • Event sourcing / ledger כפול: הנכון ביותר לכסף, אבל מורכבות שלא מוצדקת בהיקף הזה.

סנכרון בנקים: worker בבית שמושך עבודות מטבלה

הקשר

החלטה

  • ייבוא CSV ידני: בטוח לגמרי, אבל אף אחד לא עושה את זה כל שבוע.
  • Supabase Realtime במקום polling: latency נמוך יותר, אבל צריך לטפל בניתוקים ו־reconnect. עבודה שלוקחת דקות לא מרוויחה כלום מ־latency של שנייה במקום ארבע.
השלכות
  • אין פורט פתוח ברשת הביתית. הסוכן רק פונה החוצה.
  • הטבלה היא גם התור, גם הלוג וגם ה־UI: אין message broker.
  • הסנכרון עובד רק כשהמחשב דלוק.
  • ה־polling מייצר כ־21,600 שאילתות ביום. זניח בהיקף הזה.
  • משפחה אחרת צריכה Node ושורת פקודה כדי להריץ את הסוכן.
לחזור אם

ADR-07

פרטי בנק: הצפנה בדפדפן למפתח של הסוכן

הקשר

החלטה
Envelope encryption: הסוכן מייצר זוג RSA ומפרסם את הציבורי ב־bank_sync_settings.public_key. הדפדפן מייצר מפתח AES-GCM, מצפין בו את הפרטים, ועוטף אותו ב־RSA-OAEP. רק הסוכן, עם הפרטי (sync/agent-key.json), פותח. אותו קוד רץ בדפדפן וב־Node, דרך WebCrypto (sync/seal.mjs). כל כניסה מוצפנת כפריט נפרד ברשימה (sync/logins.mjs), כך ששמירה חלקית לא דורסת את השאר.

  • הצפנה בשרת עם מפתח של האפליקציה: מי שמשיג את משתני הסביבה ב־Vercel ואת המסד מקבל את כל פרטי הבנק של כולם.

  • KMS בענן: עדיין השרת זה שמפענח.
השלכות
  • Zero-knowledge מבחינת השרת והמסד.
  • התקפת החלפת מפתח: מי שמחובר לאפליקציה יכול לשים מפתח ציבורי משלו, ופרטים שיוזנו אחר כך יוצפנו אליו. המענה הוא fingerprint שמוצג במסך ונבדק מול מה שהסוכן מדפיס.
  • איבוד agent-key.json פירושו הזנה מחדש של כל הפרטים.

תוכנית יציאה מכל ספק

  • מ־Supabase: pg_dump לכל Postgres. RLS ופונקציות SQL עובדות כמו שהן. העבודה האמיתית היא להחליף את auth.uid() ואת Auth (Auth.js, Clerk), ולכתוב שכבת גישה לסוכן במקום PostgREST.
  • מ־Vercel: Next.js רץ על כל שרת Node או container. צריך להחליף את Cron (cron של מערכת או GitHub Actions) ואת ה־Git deploy.
  • מ־Anthropic: הקריאה מבודדת ב־bot.ts וב־sync/categorize.mjs. ספק אחר עם structured output הוא שינוי מקומי.
  • מ־Brevo: פונקציה אחת ב־email.ts.

חוב טכני ומסלול התפתחות

חוב ידוע במודל הנתונים

  • זיכויים בכרטיס נרשמים כ־income. נכון יותר: הוצאה שלילית באותה קטגוריה, או type = refund. היום גם ההכנסות וגם ההוצאות מנופחות.
  • העברות לחיסכון מדולגות בסנכרון. לכן הדוח מראה "נחסך ₪0". צריך לזהות העברה לחשבון חיסכון ולשייך אותה לקטגוריית החיסכון.
  • הפרשה לקרן בלי תאריכי תוקף (ADR-05). צריך טבלת allocations עם valid_from.
  • משיכה מיעד לא מורידה מהנצבר.
  • מזומן לא עובר בין חודשים.
